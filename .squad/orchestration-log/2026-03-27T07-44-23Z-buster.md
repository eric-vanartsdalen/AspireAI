## Investigation

The test creates a legacy schema (missing `file_hash` and other required columns), patches `_ensure_required_columns` to skip migration for the `files` table, and verifies that:
1. DatabaseService raises RuntimeError with detailed diagnostics
2. Error message includes database path, missing columns, schema details
3. The exception chain contains the original `sqlite3.OperationalError`

**Failure Point:** Final assertion `self.assertIsInstance(context.exception.__cause__, sqlite3.OperationalError)` was failing.

## Root Cause

Multi-candidate database initialization refactor changed exception chaining depth:

**Before:** `_ensure_database_schema` raises RuntimeError from `sqlite3.OperationalError`  
→ Exception chain: RuntimeError → OperationalError

**After:** `_initialize_database` catches exception from `_ensure_database_schema`, then raises RuntimeError  
→ Exception chain: RuntimeError → RuntimeError → OperationalError

The behavior being tested (legacy schema detection and detailed error reporting) **still works correctly**. Only chaining depth changed.

## Fix Applied

Updated test to traverse the exception chain:

```python
# Walk the exception chain to find OperationalError at root
root_cause = context.exception.__cause__
while root_cause and not isinstance(root_cause, sqlite3.OperationalError):
    root_cause = root_cause.__cause__
self.assertIsInstance(root_cause, sqlite3.OperationalError,
                      "Expected sqlite3.OperationalError in exception chain")
```

- Walking the exception chain is more robust than assuming single-level chaining
