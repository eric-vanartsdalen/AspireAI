# AspireAI Concurrent SQLite Access

This note describes how the Python service and the .NET Web app share the same SQLite file without relying on retired `documents` or `processed_documents` tables.

## Canonical shared tables

- `files` — upload and processing lifecycle
- `document_pages` — page content generated by processing

## Concurrency choices in `DatabaseService`

- Connection pooling with reusable SQLite connections
- WAL mode for mixed reads and writes
- Busy timeout for temporary lock contention
- Short write operations around status updates and page inserts

## Typical access patterns

### Python service

- Read rows where `status = 'uploaded'`
- Mark rows `processing`
- Persist `docling_document_path`, `total_pages`, and `neo4j_document_node_id`
- Insert page rows into `document_pages`
- Mark rows `processed` or `error`

### .NET Web app

- Insert new `files` rows during upload
- Read status and page data for the UI
- Avoid creating compatibility tables for Python

## Supported status lifecycle

```text
uploaded -> processing -> processed
                     -> error
```

## Notes for maintainers

- Keep transactions short.
- Prefer the canonical `files` methods in `DatabaseService`.
- Do not reintroduce sync/bridge logic for retired tables.
- If legacy tables are still present in an older database, treat them as historical only.
